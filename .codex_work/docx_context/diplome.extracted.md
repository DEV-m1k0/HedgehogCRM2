[heading 1] Введение

В современном мире информационные технологии играют важную роль в различных сферах деятельности, включая образование и управление учебным процессом. Разработка web-приложений для образовательных учреждений становится актуальной задачей, так как такие системы позволяют автоматизировать расписание занятий, учет учеников, посещаемость и работу сотрудников. Одним из таких направлений является создание CRM-системы для IT-академии, которая может быть использована не только как инструмент хранения данных, но и как средство организации учебного процесса.

Целью исследования, является проектирование и разработка web-приложения, далее (ПО), для автоматизации расписания учебных занятий и управления деятельностью IT-академии. ПО будет способствовать удобному ведению базы учеников и родителей, формированию учебных групп, контролю посещаемости, организации отработок и постановке задач сотрудникам. Также в системе предусматривается использование AI-модуля на базе GigaChat для формирования кратких сводок по ученику, рекомендаций преподавателю и генерации задач менеджеру.

Разработка web-приложения для IT-академии является актуальной задачей, поскольку она позволит предложить администраторам, менеджерам и преподавателям удобное решение для организации образовательного процесса. ПО может стать дополнительным инструментом для контроля расписания, посещаемости и учебных рисков, способствуя повышению качества работы сотрудников и своевременному взаимодействию с учениками и родителями.

Объектом исследования является – автоматизация учебного процесса IT-академии, а предмет исследования – методы и способы разработки web-приложения для управления расписанием учебных занятий, посещаемостью, отработками и задачами сотрудников.

При разработке программного обеспечения, были проанализированы различные программные решения, которые могут быть использованы для сравнения с разрабатываемым web-приложением. Далее представлен краткий обзор некоторых из них.

Универсальные CRM-системы, например, Битрикс24, amoCRM и другие подобные решения. Плюсы, широкий набор инструментов для ведения клиентов, сделок, задач и коммуникаций. Минусы, не все системы адаптированы под конкретные потребности образовательных учреждений и могут требовать дополнительной доработки для учета расписания занятий, посещаемости, групп и отработок.

Системы дистанционного обучения, например, Moodle и другие платформы для размещения учебных материалов и проведения онлайн-занятий. Плюсы, фокус на организации образовательного контента, тестировании и взаимодействии с обучающимися. Минусы, ограниченный набор возможностей для CRM-сопровождения клиентов, управления сделками, задачами менеджеров и контроля расписания очных занятий.

Электронные журналы и сервисы управления расписанием, например, приложения для фиксации занятий, посещаемости и учебных групп. Плюсы, возможность ведения расписания и контроля посещаемости в удобной форме. Минусы, сложность объединения таких сервисов с клиентской базой, задачами сотрудников, архивом данных и AI-анализом учебных рисков.

Выбор конкретного программного решения зависит от специфических потребностей образовательной организации, количества учеников, особенностей учебного процесса и обязанностей сотрудников. Разрабатываемое web-приложение может предложить более глубокую интеграцию с процессами IT-академии и объединить расписание, учеников, группы, посещаемость, отработки, сделки, задачи и AI-помощника в единой системе.

Базовые понятия и определения предметной области. В рамках разработки web-приложения «HedgehogCRM» используются следующие базовые понятия и определения:

CRM-система — CRM-система (Customer Relationship Management) — информационная система, предназначенная для автоматизации взаимодействия организации с клиентами. В контексте образовательной сферы CRM-система обеспечивает ведение базы учеников, управление сделками, задачами сотрудников и учебными процессами.

Web-приложение — Web-приложение — программное обеспечение, выполняемое на стороне сервера и доступное пользователю через браузер без установки дополнительного программного обеспечения. Взаимодействие между клиентской и серверной частями осуществляется посредством протокола HTTP.

REST API — REST API (Representational State Transfer Application Programming Interface) — архитектурный стиль взаимодействия компонентов распределённого приложения, основанный на использовании стандартных HTTP-методов (GET, POST, PATCH, DELETE) для обмена данными в формате JSON между клиентской и серверной частями системы.

IT-академия — IT-академия — образовательная организация, специализирующаяся на обучении программированию и информационным технологиям. Учебный процесс включает групповые занятия, индивидуальный контроль посещаемости, управление учебными курсами и взаимодействие с учениками и их родителями.

JWT-авторизация — JWT-авторизация (JSON Web Token) — метод обеспечения безопасности web-приложений, основанный на передаче подписанного токена, содержащего сведения о пользователе. Токен выдаётся при успешном входе в систему и используется для проверки подлинности при каждом последующем запросе к защищённым ресурсам.

Ролевая модель доступа — Ролевая модель доступа (Role-Based Access Control, RBAC) — механизм разграничения прав доступа пользователей на основе назначенных им ролей. В разрабатываемой системе определены роли администратора, менеджера, преподавателя и анонимного пользователя, каждая из которых обладает строго ограниченным набором разрешений.

Посещаемость — Посещаемость — учёт присутствия учеников на учебных занятиях. В разрабатываемой системе фиксируется статус каждого ученика (присутствовал, опоздал, отсутствовал), а также комментарий преподавателя и количество начисленных условных единиц.

Отработка — Отработка — дополнительное занятие, организуемое для ученика, пропустившего плановое занятие. Система обеспечивает назначение даты, преподавателя и группы для отработки, а также фиксацию факта её проведения.

Контейнеризация — Контейнеризация — технология изоляции приложений вместе с их зависимостями в стандартизированные программные контейнеры, обеспечивающая воспроизводимость среды выполнения независимо от операционной системы и конфигурации узла. В разрабатываемой системе применяется платформа Docker и инструмент Docker Compose.

main.py — основной файл серверного приложения. В этом файле выполняется создание экземпляра FastAPI, подключение middleware для CORS и журналирования HTTP-запросов, регистрация всех маршрутизаторов API и настройка обработки ошибок. Файл определяет корневой маршрут приложения и обеспечивает автоматическую генерацию документации Swagger UI.

db.py — модуль подключения к базе данных. В файле настраиваются SQLAlchemy engine для взаимодействия с PostgreSQL, фабрика сессий SessionLocal и базовый класс декларативных моделей Base. Модуль обеспечивает управление подключениями и транзакциями.

models.py — файл описания моделей данных. Файл содержит SQLAlchemy ORM-классы для всех сущностей базы данных: Role, User, UserSession, AuditLog, Client, Course, StudyGroup, GroupStudent, Lesson, Attendance, Deal и Task. Каждая модель определяет структуру соответствующей таблицы, типы полей, ограничения и связи между сущностями.

deps.py — файл зависимостей FastAPI. В файле реализованы функции-зависимости для внедрения в маршрутизаторы: получение текущей сессии базы данных, извлечение текущего пользователя из JWT-токена, проверка ролей пользователя и контроль доступа к защищённым маршрутам.

router.py — файл агрегации маршрутов. В файле выполняется объединение всех маршрутизаторов API-модулей (auth, users, roles, clients, courses, groups, schedule, deals, tasks, archive, admin/activity, media) в единый роутер с соответствующими префиксами и тегами OpenAPI.

services/ — каталог сервисов бизнес-логики. Каталог содержит модули обработки данных для каждой предметной области: работа с клиентами, курсами, группами, расписанием, посещаемостью, отработками, сделками, задачами, архивом и AI-модулем. Сервисы инкапсулируют бизнес-логику и взаимодействуют с моделями данных через SQLAlchemy-сессии.

Компоненты построены с использованием TypeScript и стилизованы через Sass и CSS Modules.

lib/ — каталог библиотечных модулей. Каталог содержит Axios-клиент для взаимодействия с backend API, конфигурацию TanStack React Query для управления серверным состоянием и Zustand-хранилища для управления клиентским состоянием приложения.

types/ — каталог TypeScript-типов. Каталог содержит интерфейсы и типы данных, соответствующие схемам backend API: типы для пользователей, клиентов, курсов, групп, занятий, посещаемости, сделок, задач и ответов API.

Структура программы.

Программный продукт «HedgehogCRM» состоит из трёх основных частей: серверной (backend), клиентской (frontend) и инфраструктурной. Серверная часть реализована на языке Python с использованием фреймворка FastAPI. Она включает модуль инициализации приложения (main.py), модуль моделей данных (models.py), модуль безопасности (security.py), модуль подключения к базе данных (db.py), модуль зависимостей (deps.py), агрегатор маршрутов (router.py) и одиннадцать маршрутизаторов в каталоге routes/. Клиентская часть реализована на языке TypeScript с использованием фреймворка Next.js и библиотеки React. Она включает страницы в каталоге src/app/, переиспользуемые компоненты в src/components/, модули работы с API и хранилище состояния в src/lib/. Серверная часть взаимодействует с базой данных PostgreSQL 16 через ORM SQLAlchemy. Клиентская часть взаимодействует с серверной частью через REST API по протоколу HTTP. Запросы от клиента поступают через обратный прокси Nginx, который маршрутизирует их между frontend-сервером, backend API и хранилищем медиафайлов. Все четыре компонента (nginx, frontend, backend, db) запускаются как Docker-контейнеры через Docker Compose.

Сообщения системному программисту.

В ходе выполнения настройки, проверки и эксплуатации программного обеспечения «HedgehogCRM» системному программисту могут быть выданы следующие сообщения:

[List Paragraph] HTTP 400 Bad Request — некорректный запрос к API. Действие: проверить формат и состав входных данных запроса.

[List Paragraph] HTTP 401 Unauthorized — токен доступа отсутствует, истёк или отозван. Действие: выполнить повторную авторизацию в системе.

[List Paragraph] HTTP 403 Forbidden — недостаточно прав доступа для выполнения операции. Действие: проверить роль текущего пользователя.

[List Paragraph] HTTP 404 Not Found — запрошенный ресурс не найден в базе данных. Действие: проверить корректность идентификатора записи в запросе.

[List Paragraph] HTTP 409 Conflict — конфликт данных (например, дублирование уникального значения). Действие: проверить уникальность добавляемой записи.

[List Paragraph] HTTP 422 Unprocessable Entity — ошибка валидации входных данных. Действие: проверить типы и форматы передаваемых полей.

[List Paragraph] HTTP 500 Internal Server Error — внутренняя ошибка сервера. Действие: проверить журналы командой docker compose logs backend.

[List Paragraph] "Cannot connect to the Docker daemon" — демон Docker не запущен. Действие: запустить Docker Desktop и повторить запуск командой docker compose up.

[List Paragraph] "Error: bind: address already in use" — порт уже занят другим процессом. Действие: завершить процесс, занимающий порт, или изменить порт в docker-compose.yml.

[List Paragraph] "database connection failed" — не удалось подключиться к базе данных. Действие: убедиться, что контейнер db запущен командой docker compose ps, и проверить переменную DATABASE_URL в файле .env.

from __future__ import annotations

import hashlib

import os

from datetime import UTC, datetime, timedelta

from typing import Any

import jwt

from fastapi import HTTPException, status

JWT_SECRET = os.getenv("JWT_SECRET", "change-me-in-production-very-long-random-secret")

JWT_ALGORITHM = "HS256"

ACCESS_TOKEN_MINUTES = int(os.getenv("JWT_ACCESS_MINUTES", "15"))

REFRESH_TOKEN_DAYS = int(os.getenv("JWT_REFRESH_DAYS", "14"))

def now_utc() -> datetime:

return datetime.now(UTC).replace(tzinfo=None)

def make_access_token(user_id: int, session_id: str) -> str:

exp = datetime.now(UTC) + timedelta(minutes=ACCESS_TOKEN_MINUTES)

payload = {

"sub": str(user_id),

"sid": session_id,

"type": "access",

"iat": int(datetime.now(UTC).timestamp()),

"exp": exp,

}

return jwt.encode(payload, JWT_SECRET, algorithm=JWT_ALGORITHM)

def make_refresh_token(user_id: int, session_id: str) -> str:

exp = datetime.now(UTC) + timedelta(days=REFRESH_TOKEN_DAYS)

payload = {

"sub": str(user_id),

"sid": session_id,

"type": "refresh",

"iat": int(datetime.now(UTC).timestamp()),

"exp": exp,

}

return jwt.encode(payload, JWT_SECRET, algorithm=JWT_ALGORITHM)

def decode_token(token: str, expected_type: str | None = None) -> dict[str, Any]:

try:

payload = jwt.decode(token, JWT_SECRET, algorithms=[JWT_ALGORITHM])

except jwt.ExpiredSignatureError as exc:

raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Токен истек") from exc

except jwt.InvalidTokenError as exc:

raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Некорректный токен") from exc

token_type = payload.get("type")

if expected_type and token_type != expected_type:

raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Некорректный тип токена")

return payload

def hash_token(value: str) -> str:

return hashlib.sha256(value.encode("utf-8")).hexdigest()

@router.post("/refresh", response_model=AccessTokenOut)

def refresh_access_token(

response: Response,

refresh_token: str | None = Cookie(default=None, alias=REFRESH_COOKIE_NAME),

db: Session = Depends(get_db),

) -> AccessTokenOut:

if not refresh_token:

raise HTTPException(status_code=401, detail="Refresh токен отсутствует")

payload = decode_token(refresh_token, expected_type="refresh")

session_id = payload.get("sid")

user_id_raw = payload.get("sub")

if not session_id or not user_id_raw:

raise HTTPException(status_code=401, detail="Некорректный refresh токен")

try:

user_id = int(user_id_raw)

except ValueError as exc:

raise HTTPException(status_code=401, detail="Некорректный user id в refresh токене") from exc

session = db.query(UserSession).filter(UserSession.session_id == session_id, UserSession.user_id == user_id).first()

if not session or not session.is_active:

raise HTTPException(status_code=401, detail="Сессия неактивна")

if session.refresh_token_hash != hash_token(refresh_token):

session.is_active = False

session.revoked_at = now_utc()

session.ended_at = now_utc()

db.add(

AuditLog(

user_id=user_id,

session_id=session_id,

action="auth_refresh_replay_detected",

method="POST",

path="/auth/refresh",

status_code=401,

)

)

db.commit()

raise HTTPException(status_code=401, detail="Refresh токен отозван")

if session.expires_at and session.expires_at < now_utc():

session.is_active = False

session.ended_at = now_utc()

db.commit()

raise HTTPException(status_code=401, detail="Сессия истекла")

user = db.get(User, user_id)

if not user:

raise HTTPException(status_code=401, detail="Пользователь не найден")

# Rotate refresh token on each refresh request.

new_access = make_access_token(user.id, session_id)

new_refresh = make_refresh_token(user.id, session_id)

session.refresh_token_hash = hash_token(new_refresh)

session.last_seen_at = now_utc()

db.add(

AuditLog(

user_id=user.id,

session_id=session_id,

action="auth_refresh",

method="POST",

path="/auth/refresh",

status_code=200,

)

)

db.commit()

_set_refresh_cookie(response, new_refresh)

return AccessTokenOut(access_token=new_access)

from __future__ import annotations

import logging

import os

import threading

from datetime import datetime, timedelta

from sqlalchemy.orm import Session, sessionmaker

from app.models import Lesson, StudyGroup, User

from app.services.email_service import notifications_enabled, send_plain_email, smtp_is_configured

_logger = logging.getLogger("hedgehog.reminders")

_worker_thread: threading.Thread | None = None

_stop_event: threading.Event | None = None

def _send_lesson_email(*, to_email: str, lesson: Lesson, group: StudyGroup, minutes_before: int) -> None:

start_label = lesson.start_at.strftime("%d.%m.%Y %H:%M")

subject = f"Напоминание: занятие через {minutes_before} мин"

body = (

f"Здравствуйте!\n\n"

f"Скоро начнется занятие.\n"

f"Тема: {lesson.topic}\n"

f"Группа: {group.name}\n"

f"Время начала: {start_label}\n"

f"Тип занятия: {lesson.lesson_type}\n\n"

f"Это автоматическое уведомление Hedgehog CRM."

)

send_plain_email(to_email=to_email, subject=subject, body=body)

def _process_due_reminders(db: Session) -> int:

now = datetime.now()

lessons = (

db.query(Lesson, StudyGroup, User)

.join(StudyGroup, StudyGroup.id == Lesson.group_id)

.join(User, User.id == StudyGroup.teacher_id)

.filter(

Lesson.archived_at.is_(None),

Lesson.is_cancelled.is_(False),

Lesson.reminder_minutes_before.is_not(None),

Lesson.reminder_sent_at.is_(None),

Lesson.start_at > now,

StudyGroup.archived_at.is_(None),

User.is_accepted.is_(True),

)

.all()

)

sent_count = 0

for lesson, group, teacher in lessons:

if not teacher.email:

continue

minutes_before = max(int(lesson.reminder_minutes_before or 0), 0)

remind_at = lesson.start_at - timedelta(minutes=minutes_before)

if remind_at > now:

continue

try:

_send_lesson_email(

to_email=teacher.email,

lesson=lesson,

group=group,

minutes_before=minutes_before,

)

lesson.reminder_sent_at = datetime.now()

sent_count += 1

except Exception:

_logger.exception("lesson_reminder_send_failed lesson_id=%s teacher_id=%s", lesson.id, teacher.id)

if sent_count:

db.commit()

return sent_count

def _worker_loop(session_factory: sessionmaker[Session], stop_event: threading.Event) -> None:

_logger.info("lesson_reminder_worker_started")

while not stop_event.is_set():

db = session_factory()

try:

sent = _process_due_reminders(db)

if sent:

_logger.info("lesson_reminders_sent count=%s", sent)

except Exception:

db.rollback()

_logger.exception("lesson_reminder_worker_cycle_failed")

finally:

db.close()

stop_event.wait(30)

_logger.info("lesson_reminder_worker_stopped")

def start_lesson_reminder_worker(session_factory: sessionmaker[Session]) -> None:

global _worker_thread, _stop_event

if not notifications_enabled():

_logger.info("lesson_reminder_worker_disabled notifications_off")

return

if os.getenv("LESSON_REMINDERS_ENABLED", "1").strip().lower() in {"0", "false", "no"}:

_logger.info("lesson_reminder_worker_disabled")

return

if _worker_thread and _worker_thread.is_alive():

return

if not smtp_is_configured():

_logger.warning("lesson_reminder_smtp_not_configured SMTP_HOST/SMTP_FROM are required for email sending")

_stop_event = threading.Event()

_worker_thread = threading.Thread(

target=_worker_loop,

args=(session_factory, _stop_event),

name="lesson-reminder-worker",

daemon=True,

)

_worker_thread.start()

def stop_lesson_reminder_worker() -> None:

global _worker_thread, _stop_event

if _stop_event is not None:

_stop_event.set()

if _worker_thread and _worker_thread.is_alive():

_worker_thread.join(timeout=2)

_worker_thread = None

_stop_event = None
